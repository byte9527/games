# 小游戏合集与五子棋 PWA 设计

## 1. 背景

项目从空目录开始，目标是建立一个无广告、可离线安装的小游戏合集。首个游戏为五子棋，面向日常手机使用，强调打开即玩、规则直观和本地隐私。

首版采用 PWA（渐进式 Web 应用）形态，不依赖应用商店分发。所有游戏与对局数据均在用户当前浏览器中运行和保存。

## 2. 首版目标

- 建立可持续增加新游戏的合集首页和统一页面外壳。
- 实现 15×15 休闲规则五子棋，仅支持本地双人同屏对战。
- 支持当前回合提示、胜负判定、获胜连线高亮、悔棋和重新开始。
- 自动保存未结束对局，并在用户再次打开时恢复。
- 首次成功加载后支持离线打开和游玩。
- 提供符合浏览器能力的安装入口或安装指引。
- 优先保证手机竖屏体验，同时兼容桌面浏览器。

## 3. 非目标

首版不包含以下能力：

- 人机对战或任何 AI（人工智能）棋力。
- 在线匹配、远程对战、房间或观战。
- 账号、跨设备同步、排行榜和成就系统。
- 服务端、广告、付费能力、数据统计或用户追踪。
- 五子棋禁手、段位规则或比赛计时。

## 4. 产品规则

### 4.1 棋局规则

- 棋盘为 15×15 个交叉点。
- 黑棋先手，黑白双方轮流落子。
- 双方均无禁手。
- 横、竖或任一斜线方向连续五颗或更多同色棋子即获胜。
- 棋盘下满且无人获胜时判定和棋。
- 棋局结束后不能继续落子，但允许悔棋以恢复对局。

### 4.2 操作行为

- 玩家只能在棋局进行中点击空交叉点落子。
- 悔棋每次撤销最近一手，并把回合恢复给该棋子的落子方。
- 棋局已获胜或和棋时，悔棋会重新进入进行中状态并重新计算结果。
- 棋盘已有落子时，重新开始需要二次确认；空棋盘不需要确认。
- 获胜时高亮构成胜利的连续棋子。若同一步同时形成多条五连，规则核心保留所有获胜方向，界面全部高亮。
- 终局弹窗提供“再来一局”和返回合集首页的操作。

## 5. 视觉与响应式方向

视觉采用“温润木质”方案：暖色背景、接近真实木质棋盘的配色、克制阴影和清晰的黑白棋子。整体保持安静耐看，不加入干扰游玩的动态装饰。

- 页面以手机竖屏为主要布局，棋盘始终保持正方形。
- 支持 320px 宽的小屏手机至桌面浏览器，不产生横向溢出。
- 桌面端限制棋盘最大宽度，避免棋盘被无限放大。
- 棋子除黑白颜色外，还通过轮廓、光影和当前回合文字区分。
- 控件使用足够大的触控区域；棋盘交叉点的实际点击区域覆盖相邻网格空间，不要求用户精确点击线条交点。
- 尊重系统的减少动态效果设置，胜利提示不依赖动画传达信息。

## 6. 技术选型

采用以下技术组合：

- React：构建合集页面和游戏界面组件。
- TypeScript：约束棋局状态、动作和存储结构。
- Vite：开发、构建和静态资源处理。
- CSS Grid（CSS 网格布局）：实现 15×15 棋盘交互层。
- Vitest：规则核心与存储逻辑的单元测试。
- React Testing Library：组件行为测试。
- Playwright：E2E（端到端）流程和 PWA 行为验证。

棋盘仅包含 225 个交互点，普通页面元素足以满足性能要求。首版不使用 Canvas（画布），从而保留更直接的点击处理、语义标记、响应式布局和自动化测试能力。

## 7. 架构设计

系统按职责分为五层：

1. **合集外壳**：游戏目录、路由、全局主题、页面框架和安装入口。
2. **五子棋界面**：棋盘、回合提示、控制按钮和结果弹窗。
3. **五子棋规则核心**：棋局状态、合法落子、回合切换、胜负判断和悔棋。
4. **本地存储适配器**：存档序列化、校验、恢复和清理。
5. **PWA 基础设施**：应用清单、图标、Service Worker（后台缓存脚本）和更新管理。

规则核心为纯 TypeScript 模块，不依赖 React、浏览器存储或 PWA API。界面只能通过公开的规则函数生成新状态，不能直接修改棋盘。存储适配器接收完整棋局状态，不参与规则判断。

建议的源码边界如下：

```text
src/
  app/                  # 应用入口、路由、统一布局和主题
  pages/                # 合集首页等页面
  games/
    gomoku/
      core/             # 类型、状态转换、胜负判定
      components/       # 棋盘、状态提示、控制区、结果弹窗
      storage/          # 五子棋存档适配器和数据校验
      GomokuPage.tsx    # 游戏页面组装
  pwa/                  # 安装与更新交互
  test/                 # 跨模块测试支持
```

未来新增游戏时，在 `src/games/<game-name>/` 内建立独立模块，并向合集目录注册游戏元数据，不修改五子棋内部实现。

## 8. 状态模型

棋局状态至少包含：

- 固定为 15 的棋盘尺寸。
- 225 个位置的棋盘数据，取值为空、黑棋或白棋。
- 当前玩家。
- `playing`、`won` 或 `draw` 状态。
- 可选的获胜方。
- 一条或多条获胜连线的位置集合。
- 按先后顺序记录的完整落子历史。
- 用于本地存储迁移的结构版本。

规则核心提供明确的状态转换函数，例如创建棋局、落子、悔棋和重新开始。每次操作返回新的不可变状态；非法操作返回带原因的失败结果，界面不通过异常控制正常业务流程。

## 9. 数据流

### 9.1 落子

1. 用户点击棋盘交叉点。
2. 界面把当前位置和当前棋局状态传给规则核心。
3. 规则核心验证棋局仍在进行且目标位置为空。
4. 规则核心放置棋子，并仅从最后一步向横、竖和两条斜线扫描。
5. 若任一方向连续同色棋子达到五颗，生成获胜状态及高亮位置；否则在棋盘已满时生成和棋状态；其余情况切换当前玩家。
6. React 使用新状态重新渲染界面。
7. 若棋局仍在进行，则写入活动存档；若已终局，则清除活动存档。

### 9.2 悔棋

1. 规则核心移除历史中的最后一手。
2. 当前玩家恢复为被移除棋子的落子方。
3. 清除终局结果并根据剩余历史恢复进行中状态。
4. 保存恢复后的未结束棋局；退回空棋盘时清除活动存档。

### 9.3 页面恢复

1. 五子棋页面加载时读取活动存档。
2. 存储适配器验证版本、棋盘、玩家、状态和历史的一致性。
3. 有效存档恢复到界面；无存档则创建新棋局。
4. 无效存档会被清除，并向用户显示一次明确提示。

## 10. 本地存储策略

- 使用 `localStorage` 保存单个活动棋局，不保存终局历史。
- 存储键包含应用命名空间和游戏名称，避免与未来游戏冲突。
- 存档结构包含独立版本号，为未来迁移保留入口。
- 校验不仅检查字段类型，还验证棋盘尺寸、棋子数量、落子历史与棋盘内容一致。
- 不使用宽松默认值拼凑损坏存档；无法证明有效的数据直接清除并提示用户。
- 浏览器禁止存储或容量不足时，对局继续保留在内存中，同时显示一次“自动保存不可用”的非阻塞提示。

## 11. PWA 与离线策略

- 提供应用名称、主题色、独立显示模式和完整尺寸图标。
- Service Worker 缓存应用外壳、JavaScript、CSS、图标等版本化静态资源。
- 首次成功加载后，合集首页和五子棋必须能够在断网状态下重新打开。
- 不使用在线字体、远程图片或运行时第三方资源。
- 浏览器支持安装事件时显示安装操作；不支持时展示与当前平台匹配的手动安装指引。
- 检测到新版本时提示用户更新，不强制刷新。用户主动确认后再激活新版本并重新加载，避免中断当前对局。

## 12. 异常处理

- 重复位置、终局后落子等属于可预期非法操作，由规则结果表达，不抛出异常。
- 损坏或不兼容存档会被清除，并明确告知用户无法恢复的原因类别。
- 存储写入失败不影响当前内存棋局，但明确提示自动保存不可用。
- PWA 安装能力不可用时隐藏无效按钮并提供文字指引，不伪装成功。
- 离线缓存失败时不影响当前已加载页面；再次联网后允许重试。
- UI（用户界面）层设置错误边界，捕获不可预期渲染错误并提供重新加载入口，但不吞掉开发环境错误信息。

## 13. 测试设计

### 13.1 规则单元测试

- 黑棋先手与正常黑白轮换。
- 重复位置、越界位置和终局后的非法落子。
- 横、竖、两种斜线方向的五连和超过五连。
- 棋盘边缘、角落及同一步形成多条获胜线。
- 四颗或被对方棋子隔断时不误判。
- 棋盘下满时的和棋，以及最后一步获胜优先于和棋。
- 普通悔棋、空棋盘悔棋和终局后悔棋。
- 所有状态转换不修改输入状态。

### 13.2 存储单元测试

- 正常保存、读取和清除。
- 结构版本不兼容。
- JSON 损坏、字段缺失和棋盘/历史不一致。
- 浏览器拒绝写入或容量不足。
- 终局和空棋盘不保留活动存档。

### 13.3 组件测试

- 点击空点后出现正确棋子并更新回合。
- 非法点击不改变界面状态。
- 胜利连线、结果弹窗和按钮状态正确。
- 悔棋、重新开始确认和恢复提示符合约定。
- 控件具有可识别名称，键盘操作可以触发主要按钮。

### 13.4 E2E 与 PWA 验收

- 从合集首页进入五子棋并完成一局。
- 中途刷新页面后恢复到完全一致的棋局。
- 胜利后悔棋恢复对局，再次落子可产生新结果。
- 有落子时重新开始需要确认，取消确认不会丢失棋局。
- 首次联网加载后，在离线环境重新打开应用并游玩。
- 安装清单、图标、Service Worker 注册和更新提示正常。
- 在 320px 手机视口、常见手机竖屏和桌面视口下无横向溢出。

## 14. 完成标准

满足以下条件时，首版可视为完成：

- 所有目标功能可在支持 PWA 的现代浏览器中完成，不需要服务端。
- 规则、存储和关键组件测试通过。
- 真实浏览器 E2E 流程与离线恢复验证通过。
- 手机上可以完整操作棋盘和控制按钮，无明显误触或布局溢出。
- 关闭并重新打开页面可以恢复未结束棋局。
- 项目不包含广告、统计追踪或远程运行时依赖。

## 15. 已知风险与控制

- **小屏落子精度**：15×15 棋盘在 320px 屏幕上的网格较密。通过让整个网格单元充当点击热区、突出最后落子并进行真机验收控制风险。
- **浏览器 PWA 差异**：iOS 和不同浏览器的安装入口不同。通过能力检测和平台指引适配，不假设统一安装 API。
- **存储可能被浏览器清理**：本地存储不等于永久存档。首版明确定位为“尽力恢复当前对局”，不承诺跨设备或永久保存。
- **Service Worker 更新复杂度**：旧资源与新资源可能短暂并存。通过版本化资源、用户确认更新和完整离线 E2E 测试降低风险。
